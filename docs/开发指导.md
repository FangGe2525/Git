# 物业工单通 · 开发指导

纯 Web 的物业报修与派单系统。技术栈：Spring Boot 3 + MyBatis-Plus + MySQL 8 + Spring Security/JWT，Vue 3 + Vite + Element Plus（PC 管理端），Vue 3 + Vant 4（移动 H5），DeepSeek API 做分类辅助，SSE + 短信兜底做消息推送。

---

## 一、总体结构：一个后端 + 两个前端入口

纯 Web 方案不需要小程序编译体系，前端只需两个入口，部署在同一域名下用路径区分：

| 入口 | 路径 | 使用者 | 技术栈 |
|---|---|---|---|
| 管理后台 | `/admin` | 物业客服、社区工作人员（PC 浏览器） | Vue 3 + Element Plus |
| 移动 H5 | `/m` | 业主、维修工（手机浏览器） | Vue 3 + Vant 4 |

**拆成两个独立的 Vite 项目**（如 `admin-web` 和 `mobile-web`），而不是塞进同一个项目：两端组件库、路由结构、构建产物体积差异很大，拆开后各自独立开发、独立部署，互不拖累。两者共用一个后端 API，Nginx 按路径反向代理。

### 后端分包

```
community-repair/
├── controller/          # 只做参数校验、权限注解、调用 Service
├── service/             # 业务逻辑：派单、状态流转、DeepSeek 调用
├── mapper/              # MyBatis-Plus Mapper
├── entity/  dto/        # 数据库实体与传输对象
├── security/            # JWT 过滤器、UserDetailsService
├── sse/                 # SSE 连接管理、推送服务
├── upload/              # 分片上传、合并
└── schedule/            # 定时任务：超时提醒、收费催缴
```

### 前端分目录

按 `api / router / stores / views / composables` 划分：

- `api`：集中放请求方法，与后端接口一一对应
- `composables`：可复用逻辑，如 `usePagination`、`useFileUpload`、`useTicketStatus`

即使后续增加开发人员，逻辑边界也清晰。

## 二、数据库设计

### 2.1 状态机是核心

工单流程状态为六态（含作废）：

```
PENDING 待接单 → ACCEPTED 已接单 → REPAIRING 处理中 → VERIFYING 待确认 → COMPLETED 已完成
                     ↘ 退回              ↘ 退回                ↘ 返修回处理中
任意非终态 ─────────────────────────────────────────────→ CANCELED 已作废
```

| 状态 | 可流转到 |
|---|---|
| `PENDING` | `ACCEPTED`、`CANCELED` |
| `ACCEPTED` | `REPAIRING`、`PENDING`（退回/转派）、`CANCELED` |
| `REPAIRING` | `VERIFYING`（完工提交）、`PENDING`（退回）、`CANCELED` |
| `VERIFYING` | `COMPLETED`（确认）、`REPAIRING`（返修）、`CANCELED` |
| `COMPLETED` | 终点 |
| `CANCELED` | 终点 |

**「已评价」「已收费」不是状态。** 它们与流程正交：一张单可以已评价未收费，也可以已收费未评价。流程状态止于 `COMPLETED`，评价由 `reviews` 表是否存在记录体现，收费由 `fee_status` 字段体现；前端展示层的「已评价/已收费」标签是派生出来的，不占状态位。

**转派、退回、返修、催办、超时不是状态。** 转派只改 `assigned_worker_id`（已接单状态下转派会退回 `PENDING` 让新人重新接单）；退回是回到 `PENDING` 并清空维修工；返修是 `VERIFYING → REPAIRING` 且 `rework_count++`；催办只写日志；超时是按 SLA 与时间戳**算出来**的派生事件，不落库成一个状态。

用 `ticket_logs` 表记录每一次变更的**谁、什么时候、做了什么动作、从什么状态到什么状态、备注**，这是"进度透明"的数据基础。

状态流转在 **Service 层**做合法性校验（`TicketStateMachine`）：每次变更前检查当前状态是否允许目标状态，不允许直接抛业务异常，返回 400。

### 2.2 费用状态必须与流程状态解耦

把"流程状态"和"费用状态"拆成两个字段：

- 流程状态管工单走到哪一步
- 费用状态管这单有没有产生费用、费用是否已缴

如果混在一个字段里，当维修中发现需要更换配件导致费用超出预估时，状态机就会卡死——工单既不能简单标"完成"，也不能退回"维修中"来覆盖财务记录。拆开后，工单可以正常走完流程，费用状态独立经历 `NONE → PENDING → PAID`，财务对账和催缴提醒都有独立的数据依据。

### 2.3 表结构

见 [`docs/database/schema.sql`](database/schema.sql)。核心三张表 `users` / `tickets` / `ticket_logs`：

- `media_urls` 用 JSON 字段存图片/视频的访问 URL 数组，避免单开一张关联表带来的额外 JOIN
- `skill_tags` 逗号分隔存维修工技能标签（数据量小用 `FIND_IN_SET` 够用，后期再拆关联表）

## 四、各端关键实现要点

### 4.1 扫码报修的 URL 设计

二维码里放**普通 URL**，而不是小程序码：

```
https://repair.your-community.com/m/report?point=B3-1201
```

业主用手机相机或微信"扫一扫"直接打开 H5 报修页，`point` 参数自动带入楼栋和房号，业主只需填写故障描述和上传照片。每个楼栋、单元或设备点位生成一个独立二维码，打印张贴即可。

### 4.2 文件上传：先直传，再分片

**第一版直传**：限制图片最长边 1920px（前端 Canvas 压缩）、视频不超过 20 MB 或 15 秒。H5 用 Vant 的 `Uploader` 组件或原生 `<input type="file" accept="image/*" capture="environment">` 调起手机相机。

**第二版分片**：前端把文件切成 1–2 MB 的块逐块上传；后端接收全部分片后按序号升序合并，并用 MD5 或 SHA-256 做全量校验。核心收益是**失败只重传单个分片**，而不是整个视频重来。文件小于 100 MB 时继续走直传，超过阈值再走分片。

后端合并分片时，用 `FileChannel.transferFrom()` 按 `chunk_number` 升序高效拼接，比逐块读写更省内存。

### 4.3 自动派单：DeepSeek 只做"读懂"，规则做"决定"

工单创建后，后端将 `category + description` 发给 DeepSeek，要求返回结构化 JSON：

```json
{"category": "水电", "priority": "HIGH", "skill": "电工"}
```

拿到 JSON 后**规则派单**：查询 `role='WORKER'` 且 `skill_tags` 包含模型建议技能的维修工，按当前 `REPAIRING` 状态工单数量升序，分配给负载最低的人。

如果模型输出格式异常或找不到匹配技能的人，**回退到客服手动派单**。

关键原则：不要让模型直接"决定派给谁"。模型负责语义分类和优先级判断，派单决策由代码根据确定性规则完成，避免把电梯故障派给没有电梯维修资质的工单人员。

### 4.4 消息推送：SSE 做实时，短信做兜底

纯 Web 没有微信订阅消息，推送分三层：

**① 站内通知（必做，零成本）**
工单状态变更时向 `notifications` 表插入记录，业主打开 H5 时在"我的工单"右上角展示未读角标。

**② SSE 实时推送（页面打开时实时刷新）**
Spring MVC 原生支持 `SseEmitter`，不需要引入 WebFlux 或 WebSocket。实现要点：

- Controller 方法返回 `SseEmitter`，`produces = MediaType.TEXT_EVENT_STREAM_VALUE`
- **超时设为 0L**，否则 Tomcat 默认约 30 秒就会掐断连接——这是"连上就断"最常见的坑
- **三个回调一个不能少**：`onCompletion`、`onTimeout`、`onError` 都要从连接登记表中移除连接，否则会积攒僵尸连接
- 建连后**立刻发一行注释**作为首包，让浏览器和中间代理尽早见到字节
- 生产环境需要**心跳**，定期发送注释行保活，防止 Nginx 等代理因空闲超时断开

前端在页面打开时用原生 `EventSource` 订阅，按 `event` 类型监听 `ticket-status` 事件，收到后刷新工单详情或更新时间线。SSE 是单向推送，恰好匹配"工单状态变更 → 通知业主"的场景，不必为通知类需求引入双向 WebSocket 的复杂度。

**③ 短信兜底（关键节点）**
页面关闭后 SSE 即断开，所以对 **"已派单"** 和 **"待验收"** 两个关键节点，调用阿里云或腾讯云短信发送简短通知。前者影响业主对响应速度的感知，后者需要业主操作，漏掉的代价最高。

### 4.5 PC 管理后台

核心页面：工单列表（Element Plus 表格 + 筛选 + 分页）和工单详情。

详情页从 `ticket_logs` 读取记录，用 `el-timeline` 渲染状态时间线，展示"什么时候派的单、谁在修、修到哪一步"。

接口：`PUT /api/tickets/{id}/assign` 派单，`PUT /api/tickets/{id}/status` 变更状态，每次变更由后端写入 `ticket_logs`。

### 4.6 统计图表：ECharts 按需引入

统计页展示近 30 天报修量趋势、故障分类占比、平均响应时长、维修工完工量、收费状态分布。

用 ECharts 5，**务必按需引入**（全量约增加 600 KB）：

```typescript
// utils/echarts.ts
import * as echarts from 'echarts/core';
import { LineChart, PieChart, BarChart } from 'echarts/charts';
import { TitleComponent, TooltipComponent, GridComponent, LegendComponent } from 'echarts/components';
import { CanvasRenderer } from 'echarts/renderers';

echarts.use([LineChart, PieChart, BarChart, TitleComponent, TooltipComponent, GridComponent, LegendComponent, CanvasRenderer]);
```

封装 `BaseChart.vue`，用 `ResizeObserver` 监听容器尺寸变化并调用 `resize()`，组件卸载时调用 `dispose()` 防止内存泄漏。后端提供一个聚合接口返回各维度统计，前端只负责渲染。

### 4.7 权限控制

后端 Spring Security + JWT，JWT 中携带 `roles` claim，接口上用 `@PreAuthorize("hasRole('CS')")` 校验。

前端路由用 `meta.roles` 配合全局前置守卫：`OWNER` 和 `WORKER` 进入移动 H5，`CS` 和 `COMMUNITY` 进入管理后台。两端部署在不同路径时，登录成功后按角色重定向到对应入口，无权访问时提示或跳转。

### 4.8 完工确认、评价与收费提醒

维修工在 H5 将工单置为 `VERIFYING`，业主在"我的工单"点击确认完工，工单进入 `ARCHIVED`，随后弹出 1–5 星评价。

超过 **72 小时**未确认，定时任务自动归档并记录"超时未确认"。

收费提醒用 `@Scheduled` 每天扫描 `fee_status='PENDING'` 且超过约定缴费日的工单，触发短信或站内通知。

注意区分**维修费**（工单产生）和**周期性物业费**，两者建议分表或分类型存储，催缴策略可以不同。

## 六、部署要点

前后端分离部署，Nginx 作为统一入口：静态前端走 `/`（或 `/admin`、`/m`），`/api/` 反代到 Spring Boot 的 `127.0.0.1:8080`，SSE 端点 `/sse/` 同样反代。

**Nginx 必须为 SSE 关闭代理缓冲**，否则事件会被缓冲而无法实时到达浏览器；同时设置足够的 `proxy_read_timeout`：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

location /sse/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}
```

后端用 systemd 或 nohup 启动 JAR，MySQL 单独服务。

上线前确认：

- JWT 密钥通过环境变量注入
- DeepSeek API Key 不在代码仓库中
- 上传目录有写权限
- Nginx 已配置 HTTPS（移动端浏览器的相机和定位 API 在非 HTTPS 下可能受限）

## 七、本仓库的实施约定

原始方案有两处需要修正，已在实现中采用：

1. **SSE 鉴权用 JWT 而非 uid**：原设计为 `/sse/subscribe?uid={userId}`，任何知道 uid 的人都能监听他人工单。改为 `?token={JWT}`，后端校验后取用户 id（`EventSource` 无法自定义请求头，这是唯一可行解）。
2. **`role` 单值字段的局限**：客服往往兼任社区工作人员，单值 `ENUM` 无法表达。v1 先保持单角色，后续如需多角色再加 `user_roles` 关联表。

其余约定：

- `skill_tags` 逗号分隔、`media_urls` JSON 字段均按原方案实现
- 状态流转校验集中在 `TicketStateMachine`，非法流转抛 `BusinessException`
- 统一响应结构 `{code, message, data}`，`code=0` 为成功
- 分阶段推进，每阶段一个 commit 并推送

## 一句话收束

这套纯 Web 方案的开发链路比小程序方案更短——两个 Vue 前端共用一套后端，扫码用 URL 代替小程序码，SSE 代替订阅消息，短信补足离线触达。核心复杂度集中在**工单状态机**和**派单规则**上，DeepSeek 只负责把"业主的描述"翻译成结构化分类，不要让它越过规则直接决策。
